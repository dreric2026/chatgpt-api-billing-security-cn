## **核心问题：怎样让 GitHub 文档既能审计充值事故，又不会泄露敏感资料或诱导自动重付？**

## 1. 仓库应该保存什么，不应该保存什么？

保存流程、字段定义、虚构事件、校验脚本和公开规则来源；不保存真实账单截图、完整邮箱、订单号、卡资料、密码、验证码、恢复码、Cookie 或 API 密钥。

真实事件只在工单中使用脱敏编号引用，仓库无法反推出个人身份。README 明确数据边界，新贡献者提交前必须阅读。

## 2. YAML 事件的最小字段是什么？

包括 schema_version、event_id、account_alias、channel、target_plan、product_scope、state、last_evidence_at、owner 和 entitlement_verified。金额若记录，必须带币种、来源和核对时间。

state 使用枚举，禁止用 done、maybe、seems_ok 等模糊词。时间采用含时区格式，便于支持人员重建顺序。

## 3. 为什么付款动作不应出现在 GitHub Actions？

CI 可以验证文件、运行测试、生成脱敏报告，但不能登录账号、提交付款、开启自动购买、取消订阅或申请退款。代码仓库的自动化权限不应覆盖财务动作。

任何 `retry_payment`、`purchase` 或敏感字段都由 linter 阻止。GitHub Actions 只对合并请求给出通过或失败。

## 4. 如何表示 Plus、Pro 与 Codex 的关系？

target_plan 记录 Plus 或 Pro，product_scope 记录 subscription、codex_credits 或其他明确范围。两者不能互相推断。

Codex充值事件必须写 source_page 与 account_alias，避免把 API 组织账单或另一个工作区的用量混入个人订阅。

## 5. 充值失败状态机怎样写入 Runbook？

从 submitted 进入 pending、ordered、verified、failed 或 review。timeout 只能进入 pending；资金完成但无订单进入 review；订单存在但账号不符也进入 review。

只有订单、账号和权益全部一致，才能 verified。旧渠道活动状态仍未知时，事件不能 closed。

## 6. CI 如何扫描敏感字段？

校验器遍历 YAML 键名与字符串，拦截 password、otp、cookie、card_number、cvc、recovery_code 等字段，并检测可能的完整邮箱。示例数据使用 example.invalid 或不可还原别名。

扫描只是最后一道防线，不能替代人工审查。截图与二进制文件默认禁止进入 incidents 目录。

## 7. Pull Request 必须回答哪些问题？

说明改变了哪个决策点、依据什么公开规则、是否影响旧事件、是否新增外部动作。审查者用虚构案例走完整流程，确认查询与付款没有混在一起。

价格、额度、成功率等易变数字若无当天证据，应删除并改为实时页面核对。

## 8. 扣款未到账的 P2 Runbook 怎样执行？

第一步冻结新购买；第二步按资金、订单、身份、权益收集脱敏证据；第三步指定唯一 owner；第四步联系正确渠道；第五步排查重复订阅。

Runbook 不规定固定等待分钟数，也不建议跨渠道重付。支持回复进入时间线后，负责人才能改变状态。

## 9. 账号交接为什么要记录原登录方式？

昵称和显示邮箱可能不足以识别账号，尤其是多个 Google、Apple 或工作账号并存时。交接只写登录方式与脱敏别名，不交接密码。

新负责人应亲自登录并核对 Billing、Usage 与原渠道；无法确认时把事件标为 review，而不是补写猜测。

## 10. 如何做版本化和月度复核？

每次规则变化提升 schema_version，并在 changelog 说明。事件引用当时使用的 Runbook 版本，避免后来规则覆盖历史判断。

每月复核链接、字段与禁用词，删除过期固定信息。仓库内容可以长期搜索，但事实核对必须面向当天页面。

## 11. 如何把服务入口放进公开文档？

资源链接可以放在文首和文尾，但必须与核对提醒相邻：确认账号、套餐、实时费用、周期、到账和异常规则。不能把外链写成保证成功的结论。

文档不得要求读者提交凭据。任何服务交付仍由账号持有人自行验收。

## 仓库结构示例：让规则、样例与事故分离

建议把仓库拆成 schemas、examples、scripts、runbooks 与 docs 五层。schemas 只定义字段和枚举；examples 只放完全虚构事件；scripts 运行 linter 与单元测试；runbooks 描述充值失败、重复扣款、账号错位和交接流程；docs 解释术语与维护政策。真实事件不进入任何目录，只通过不可还原编号在受控工单引用。

每个 YAML 文件都要带 schema_version 和 reviewed_at。CI 先验证 YAML 可解析，再验证必填字段、状态跳转与禁用词，最后检查文首文尾链接和日期。若来源页面超过规定复核窗口，CI 给出警告但不自动替换数据；维护者必须打开实时页面重新确认。

## 一个最小 GitHub Actions 工作流应该做什么？

工作流只执行三步：安装本地校验依赖、运行虚构样例测试、扫描禁止字段。它不读取浏览器会话，不访问账单后台，不上传截图，也不生成付款链接。Secrets 中不放账号密码、验证码或支付信息，因为自动化根本不需要这些数据。

分支保护要求校验通过和至少一位审查者批准。审查者重点看新增动作是否改变外部状态、状态机是否把 timeout 误作 failed、示例是否可能指向真实用户。任何自动购买、自动取消、自动退款或跨渠道重试建议都应阻止合并。

## 交接演练：负责人离开前必须完成什么？

旧负责人先列出账号别名、原登录方式、购买渠道、当前方案、下一日期、产品范围和最后核对时间。新负责人不接收密码，而是由账号持有人在场登录并确认。无法核对的字段标记 unknown，不能用口头“应该是”填满。

随后用一个虚构事件演练：网页超时、银行待处理、渠道稍后成单、目标账号错误。新负责人按 Runbook 冻结购买、查询证据、进入 review，再在正确账号找到订单。演练结束后，双方确认谁拥有后续决策权，避免两个人同时处理同一异常。

## 为什么要把公开规则来源写进提交记录？

订阅、credits、可用范围和页面入口会变化。提交信息应写核对日期和来源类型，但不把固定价格变成永久常量。规则变化时提交新版本，旧事件仍引用当时版本，审计者可以解释当时为什么做出某个判断。

月度维护者检查失效链接、旧术语、过期阈值和不再适用的案例。无法核实的数字删除，改为目标账号实时页面；封面、README 和 SEO 描述也不得承诺成功率或排名。

仓库发布前最后运行一次文档链接检查与 Markdown 预览，确认表格、代码块、FAQ、目录和首尾资源入口正常。外链失效只影响文档状态，不应触发任何替代付款动作；维护者修复链接后重新提交审查。

## 可理解或可运行的示例

下面的示例只管理脱敏状态或生成建议，不连接付款页面，也不保存密码、验证码、恢复码、Cookie、完整卡号或安全码。

```python
FORBIDDEN = {"password", "otp", "cookie", "card_number", "cvc", "recovery_code"}

def validate(event: dict) -> list[str]:
    errors = []
    keys = {str(k).lower() for k in event}
    if keys & FORBIDDEN:
        errors.append("事件包含禁止字段")
    if event.get("state") == "verified" and not event.get("entitlement_verified"):
        errors.append("缺少目标账号权益验收")
    if event.get("action") in {"purchase", "retry_payment"}:
        errors.append("仓库自动化不得执行付款")
    return errors
```

## 常见问题 FAQ

### Q1：公开仓库能放账单截图吗？

不应，使用虚构样例和脱敏事件摘要。

### Q2：CI 可以自动重新充值吗？

不能，CI 只校验规则与文件。

### Q3：Plus 与 Pro 用同一个字段吗？

可用 target_plan 枚举，但事件意图必须固定。

### Q4：Codex credits 怎么记录？

用独立 product_scope 和实时页面来源。

### Q5：页面超时能标记 failed 吗？

不能，先进入 pending 并查询证据。

### Q6：为什么还要人工审查？

扫描器无法理解所有上下文和外部状态。

### Q7：真实事件如何引用？

只用不可还原事件编号，证据留在受控工单。

### Q8：历史价格要不要保留？

审计可保留核对时间，但公开教程不应把旧值当当前事实。
