## 1. 这个仓库模块解决什么问题？

模块只做三件事：描述工作负载、根据公开规则输出建议、保存付款前后检查记录。它不抓取账号数据，不保存密码，也不调用支付接口。

这样能保持安全边界：人负责登录和付款，脚本负责整理决策证据。

推荐把它放在团队运营仓库或个人工具仓库，而不是为每篇文章新建一个空仓库。

## 2. 目录怎样设计才便于长期维护？

可以使用 config、scripts、reports 和 docs 四个目录。config 保存工作负载画像；scripts 保存选择器；reports 保存每周期复盘；docs 保存充值和安全规范。

不要提交账单截图、邮箱全名或支付信息。报告只保留脱敏账号标识、日期、方案和结果。

目录越简单越容易坚持，第一版不要引入数据库和复杂部署。

## 3. YAML画像应该包含哪些字段？

最小字段包括：统计周期、每周任务量、长任务数量、仓库任务数量、平均返工分钟、关键交付数量。还可增加角色和项目标签。

字段要描述自己的工作，不要填写网上流传的套餐额度。脚本只比较相对负载，真实权益仍由目标账号实时页面决定。

每次续费前复制一份新画像，保留历史而不是覆盖旧数据。

规则只输出“评估建议”，不输出“必须购买”。因为同样的负载还可能通过拆分任务、调整排期或改进测试来解决。

## 12. 用 CI 检查画像，而不是检查付款

持续集成可以验证 YAML 结构、字段类型和测试样例，但不应该登录账号或执行充值。把边界写在 README 中：自动化只检查决策输入，人负责实时页面核对与最终付款。

## 常见问题 FAQ

### 1. 为什么不用脚本自动购买？

付款与账号验证需要人工确认。脚本只整理证据和建议，更符合安全边界。

### 2. YAML阈值是官方额度吗？

不是，它只是团队自定义的负载阈值；真实能力与规则以账号页面为准。

### 3. 公开仓库能保存充值记录吗？

只建议保存脱敏模板和样例，真实账号、订单与账单证据应放在受控私有位置。

### 4. Plus和Codex会同时被推荐吗？

可能，因为一个描述日用基线，一个描述仓库任务。最终要结合账号实时状态判断。

### 5. 需要安装复杂依赖吗？

第一版可只用 YAML 解析库与简单脚本，重点是数据口径与复盘。

### 6. 充值失败状态怎样表示？

使用明确枚举，例如 FAILED_PAYMENT、PENDING_SYNC、BLOCKED_USER_ACTION，并附时间。

### 7. 脚本能替代人工验收吗？

不能。账号、账单和功能入口仍需人工在目标账号确认。

### 8. 什么时候删除历史画像？

通常不必删除；保留脱敏历史有助于比较，但敏感证据应按安全策略定期清理。
